# V0.0 Engineering Interface

This document records the v0.0 implementation contract for the DataFrame-first
toy implementation of `agent-memory`.

It is not the final public API reference. It describes the engineering
boundaries needed to turn DataFrame-style memory policies into executable
semantic view maintenance. The golden API and theory documents remain:

- `docs/design/operator-api.md`
- `docs/optimization/incremental-semantic-view-maintenance.tex`

The goal of v0.0 is to make the current story executable without prematurely
building storage backends, schema classes, lazy scheduling, DSPy optimization, or
a full query optimizer.

## 1. Goal

v0.0 should demonstrate the core project thesis:

1. Users define memory as dataframe-style view definition queries `Q`.
2. The system records those view definitions as internal logical query objects.
3. A memory view maintenance planner derives hardcoded differential maintenance
   queries `Q'`.
4. A runtime executes those maintenance queries through a semantic execution
   adapter.
5. Materialized memory state is held in in-memory dataframes.

The implementation should be clean enough to extend, but small enough that each
interface has a real v0.0 use.

## 2. Layered Architecture

### User Surfaces

v0.0 has two user surfaces.

End users use built-in memories:

```python
import agent_memory as am


memory = am.ClaudeMemory()
memory.add("Please remember that I prefer concise design docs.")
memory.add(am.Message(content="Please remember that I prefer concise design docs."))
results = memory.query("design docs")
```

`add(...)` and `query(...)` are intentionally asymmetric. `add(...)` is a
generic end-user append surface for messages or events. A string is
`Message(content=...)` sugar, and the runtime is responsible for normalizing
message objects into the policy's log shape.

v0.0 message-to-log column convention:

- `Message.content` writes to the log column named `"message"`.
- `Message.role`, `Message.timestamp`, `Message.session_id`, and
  `Message.metadata` write to same-name log columns when present.
- Platform-native message objects are not interpreted by core `Memory`; a future
  agent-platform adapter should convert them into `am.Message` or a mapping.

By contrast, `query(...)` is policy-owned retrieval behavior. A concrete memory
policy should construct the semantic query plan it wants to expose instead of
relying on the base runtime to guess a target view. In v0.0, a built-in memory
may return a plan such as `catalog.sem_topk(query, 5)`. The framework
automatically hands returned `Relation` plans to the runtime query execution
shell, which still raises `NotImplementedError` until execution exists.

Policy authors define memory policies with DataFrame-style view queries:

```python
import agent_memory as am


class ClaudeMemory(am.Memory):
    log = am.Log()

    topics = (
        log
        .sem_flat_map(
            output_cols={
                "topic_name": "Candidate durable memory topic name.",
                "topic_content": "Candidate durable memory content.",
            },
            instruction=(
                "Extract zero or more durable memory topic candidates from "
                "{message}, filling {topic_name} and {topic_content}."
            ),
        )
        .select(["topic_name", "topic_content"])
        .sem_groupby(
            key=["topic_name"],
            instruction="Find candidates related to the same durable memory topic.",
        )
        .sem_agg(
            input_cols=["topic_name", "topic_content"],
            output_cols={
                "topic_name": "Canonical durable memory topic name.",
                "topic_content": "Merged durable memory content.",
            },
            instruction="Choose a canonical topic name and merge topic content.",
        )
        .select(["topic_name", "topic_content"])
    )

    catalog = (
        topics
        .sem_map(
            input_cols=["topic_name", "topic_content"],
            output_cols={
                "catalog_title": "Title shown in the memory catalog.",
                "path": "Relative path to the topic memory file.",
                "hook": "One-line relevance hook.",
            },
            instruction="Produce one catalog row per topic.",
        )
        .select(["catalog_title", "path", "hook"])
    )

    def query(self, query: str):
        return self.catalog.sem_topk(query, 5)
```

Policy-author public objects:

- `am.Memory`
- `am.Log`
- `am.Message`
- dataframe-style operators such as `select`, `filter`, `assign`, `concat`,
  `union`, and `subtract`
- semantic operators such as `sem_filter`, `sem_map`, `sem_flat_map`,
  `sem_groupby`, `sem_agg`, `sem_join`, and `sem_topk`

`sem_agg(...)` is a dataframe-style semantic operator. `Relation.sem_agg(...)`
means whole-relation aggregation; `GroupedRelation.sem_agg(...)`, produced by
`sem_groupby(...)`, means per-group aggregation. v0.0 uses the chain form
`sem_groupby(...).sem_agg(...)` rather than a top-level imported aggregate
helper.

The policy-author query shape is DataFrame-first. v0.0 does not require users to
define Pydantic schemas or typed memory node classes. `am.Log()` uses a default
DataFrame-like log shape; explicit column declarations can be added later while
staying in DataFrame form.

### Logical Query Model

The logical query model is internal. It records the view definition queries
written through the authoring API.

Core objects:

- `Log`: base source relation, not a memory view.
- `Relation`: dataframe-like authoring handle returned by operators, not a
  top-level public object.
- `GroupedRelation`: intermediate chain handle returned by `sem_groupby(...)`;
  it becomes a normal `Relation` after `.sem_agg(...)`.
- `RelationExpr`: internal immutable expression node.
- `MemoryView`: named derived memory view collected from a `Memory` class.
- `MemorySpec`: collected declaration for one memory class.

`RelationExpr` should represent operators such as:

- source relations: `log`
- runtime delta source relations: `delta_log`, representing rows appended since
  the last maintenance step. v0.0 has one log per memory, so `delta_log` is
  unambiguous; multi-log memories are out of scope.
- named memory view references
- ordinary operators: `select`, `filter`, `assign`, `concat`, `union`,
  `subtract`, `drop_duplicates`
- semantic operators: `sem_filter`, `sem_map`, `sem_flat_map`,
  `sem_groupby`, `sem_agg`, `sem_join`, `sem_topk`

`Relation` is the dataframe-like handle used while authoring a policy. It
exposes methods such as `sem_map`, `sem_groupby`, and `select`.
`RelationExpr` is the immutable logical node inside a `Relation`; it records the
operator name, inputs, parameters, and column metadata. Policy authors use
relation methods, but they do not instantiate or inspect `RelationExpr`.
`Relation.expr` is currently readable as an internal observation detail for
tests and debugging, but policy authors should not treat it as stable public API.

Class body collection follows these rules:

- `am.Log()` defines the source relation. It is the base table, not a
  `MemoryView`.
- A class attribute whose value is a `Relation` and whose name starts with `_`
  is treated as a private intermediate relation. It can be referenced by later
  view definitions, but is not collected as a public memory view.
- A class attribute whose value is a derived `Relation` and whose name does not
  start with `_` is collected as a `MemoryView`.
- Non-`Relation` class attributes are ignored by the memory view collector.

For example, `log` is the source relation, and derived public memory relations
such as `topics` and `catalog` are collected as `MemoryView`s. A policy may also
declare private intermediate relations by prefixing a relation name with `_`.

`MemoryView` is the preferred name for named memory views. Avoid `ViewDef` in
v0.0 because the project vocabulary is memory-centered. Avoid `ViewGraph` in
v0.0; dependency information can be derived from `MemorySpec` and relation
expressions when needed.

### Memory View Maintenance Planner

`MemoryViewMaintenancePlanner` is the core internal `Q -> Q'` component.
Policy authors and end users do not call it directly.

Responsibilities:

- accept a `MemoryView` full definition query `Q`
- apply hardcoded differential rules from the golden theory document
- produce a maintenance relation expression `Q'`
- keep rewritten instructions explicit and inspectable

v0.0 should implement rule-based rewrites directly in Python. It should not
introduce Calcite or a general rule engine yet.

The planner name should stay memory-specific:

```python
class MemoryViewMaintenancePlanner:
    ...
```

`IVMRewriter` is acceptable as an internal helper name, but not as the main
component name. The main component should leave room for future rule selection,
cost estimation, backend capability checks, and instruction rewriting.

v0.0 planning unit:

- `MemoryViewMaintenancePlanner.plan(view, delta)` produces a maintenance query
  for one memory view.
- For cascaded views, such as `catalog` depending on `topics`, the future runtime
  is responsible for invoking the planner in dependency order and feeding an
  upstream view delta into the next view's maintenance step.
- v0.0 does not implement multi-view fan-out planning or cross-view rule
  sharing.

### Memory Runtime

`MemoryRuntime` orchestrates v0.0 execution.

Responsibilities:

- append new log rows
- normalize end-user append input such as string messages into the configured
  log columns
- identify affected memory views
- ask `MemoryViewMaintenancePlanner` for maintenance queries
- call an `ExecutionAdapter`
- update in-memory dataframe state
- support write-side maintenance for end-user methods such as `add(...)`

v0.0 can run eagerly on each appended log batch. Do not build a scheduler
hierarchy yet. Lazy, batched, query-triggered, and freshness-aware maintenance
belong to future runtime work.

`MemoryRuntime` owns materialized memory state. `MemorySpec` remains the logical
policy declaration and should not carry runtime dataframe contents. The v0.0
interface layer may keep only a private in-memory state placeholder until execution is
implemented. The intended state keys are `"log"` for the source log and
`MemoryView.name` values for public materialized views; private intermediate
relations are not guaranteed to be materialized.

Retrieval remains policy-owned in v0.0. `MemoryRuntime` does not route
`query(...)` calls or choose a target view; the framework only passes it a
`Relation` plan after a concrete memory policy returns one from `query(...)`.

Internal debugging hooks may exist during development, but `view(...)`,
`explain(...)`, and `explain_maintenance(...)` are not v0.0 public API.

### Execution Adapter

`ExecutionAdapter` is the internal boundary between agent-memory logical plans
and a semantic operator execution engine.

v0.0 should implement only:

- `LotusAdapter`

`LotusAdapter` lowers supported logical expressions to LOTUS-style dataframe
operators and executes them. v0.0 uses Lotus as the default semantic execution
mechanism internally. DeepSeek is only model/provider configuration inside this
adapter; it is not an agent-memory architecture layer.

API keys should come from environment variables or the model provider's standard
configuration path. v0.0 may use Lotus plus DeepSeek for smoke demos, but
ordinary public examples should not require users to pass a `LotusAdapter`.

v0.0 adapter input contract:

- `expr` is a logical `RelationExpr` produced by the planner.
- `inputs` uses the same key convention as runtime state: `"log"` for the source
  log, `"delta_log"` for rows appended since the last maintenance step, and
  `MemoryView.name` values for public materialized views.
- The runtime is responsible for populating inputs required by the expression;
  adapters may raise if a referenced input is missing.

## 3. V0.0 Execution Path

The intended flow is:

1. A policy author defines a subclass of `am.Memory`.
2. The authoring API builds `Relation` objects during class definition.
3. The memory class collector builds a `MemorySpec`.
4. The collector identifies derived memory views such as `topics` and `catalog`;
   private intermediate relations remain internal query expressions.
5. `MemoryRuntime` receives new log rows.
6. `MemoryViewMaintenancePlanner` derives the maintenance query `Q'` for affected
   views.
7. `LotusAdapter` executes the rewritten semantic query.
8. `MemoryRuntime` updates in-memory dataframe state.

Minimal usage:

```python
memory = am.ClaudeMemory()
memory.add(am.Message(content="Please remember that I prefer concise design docs."))
results = memory.query("design docs")
```

This is the intended surface. In the current v0.0 interface layer, both write-side
maintenance and retrieval execution still raise `NotImplementedError`.

## 4. V0.0 Boundaries

Do not implement these in v0.0:

- user-defined schema classes
- DSPy prompt/program optimization
- lazy/eager/batched scheduler hierarchy
- multiple storage backends
- Calcite integration
- Palimpzest adapter
- graph/vector/markdown stores
- long-term persistence beyond in-memory dataframe state

These are future extension points, not empty interfaces that v0.0 must create.

The code should leave room for those extensions by keeping boundaries clean:

- planner logic should not import LOTUS directly
- adapter logic should not know about Python memory class collection
- runtime logic should call adapters through `ExecutionAdapter`
- model/provider config should stay inside adapter configuration
- memory state should be isolated enough to replace with storage backends later

## 5. Naming Summary

Preferred public / policy-author names:

- `Memory`
- `Log`
- dataframe-style ordinary operators
- dataframe-style semantic operators

Preferred internal engineering names:

- `Relation`
- `GroupedRelation`
- `RelationExpr`
- `MemoryView`
- `MemorySpec`
- `MemoryRuntime`
- `MemoryViewMaintenancePlanner`
- `ExecutionAdapter`
- `LotusAdapter`

Avoid in v0.0:

- `ViewDef`
- `ViewGraph`
- `SemanticMemoryView`
- `SemanticViewRuntime`
- `DspyOptimizer`
- `CalcitePlanner`
- `StorageBackend`
- `Scheduler`

Use `semantic` mainly for operators and execution semantics, not for every class
name.
