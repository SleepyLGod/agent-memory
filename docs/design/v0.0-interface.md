# V0.0 Engineering Interface

This document records the v0.0 implementation contract for the DataFrame-first
toy implementation of `agent-memory`.

It is not the final public API reference. It describes the engineering
boundaries needed to turn DataFrame-style memory policies into executable
semantic view maintenance. The golden API and theory documents remain:

- `docs/design/operator-api.md`
- `docs/optimization/incremental-semantic-view-maintenance.tex`

The goal of v0.0 is to make the current story executable without prematurely
building storage backends, schema classes, lazy scheduling, DSPy optimization, or
a full query optimizer.

## 1. Goal

v0.0 should demonstrate the core project thesis:

1. Users define memory as dataframe-style view definition queries `Q`.
2. The system records those view definitions as internal logical query objects.
3. A policy-level compiler derives hardcoded differentiated maintenance queries
   `Q'`.
4. A runtime loads the in-memory differentiated policy and executes those
   queries through a semantic execution adapter.
5. Materialized memory state is held in in-memory dataframes.

The implementation should be clean enough to extend, but small enough that each
interface has a real v0.0 use.

## 2. Layered Architecture

### User Surfaces

v0.0 has two user surfaces.

End users use built-in memories:

```python
import agent_memory as am


memory = am.ClaudeMemory()
memory.add("Please remember that I prefer concise design docs.")
memory.add(am.Message(content="Please remember that I prefer concise design docs."))
results = memory.query("design docs")
```

`add(...)` and `query(...)` are intentionally asymmetric. `add(...)` is a
generic end-user append surface for messages or events. A string is
`Message(content=...)` sugar, and the runtime is responsible for normalizing
message objects into the policy's log shape.

v0.0 message-to-log column convention:

- `str` input is normalized as `{"message": text}`.
- `Message.content` writes to the log column named `"message"`.
- `Message.role`, `Message.timestamp`, `Message.session_id`, and
  `Message.metadata` write to same-name log columns when present.
- `Message.metadata` remains one nested `"metadata"` cell; it is not expanded
  into separate dataframe columns.
- `add(...)` also accepts a column-keyed mapping for callers that already have
  dataframe-style row data.
- `Log(..., system_columns=True)` opts into framework-owned `_row_id`,
  `_added_at`, and `_add_seq` columns. Runtime generates them at append time;
  callers cannot provide or override these reserved names.
- `_add_seq` resumes from the restored log length. It is append order, not
  event time; policies still need `reference_time` / `valid_at` for event-time
  semantics.
- Fields not declared in `Log({...})` are currently preserved in the in-memory
  pandas row rather than rejected. v0.1 should decide whether runtime enforces
  the declared log schema.
- Platform-native message objects are not interpreted by core `Memory`; a future
  agent-platform adapter should convert them into `am.Message` or a mapping.

Maintenance is eager unless the caller explicitly chooses a count-based
refresh boundary:

```python
memory = ClaudeMemory(refresh=am.CountRefresh(every=32))

memory.add(event)
print(memory.pending_count)
memory.flush()
```

With this configuration, `add(...)` normalizes and buffers each source row.
Reaching 32 pending rows synchronously runs the full differential DAG once with
one multi-row delta. `flush()` publishes a shorter tail. The refresh is atomic:
on failure, the current view remains unchanged and the pending rows remain
available for retry.

`query(...)` does not flush. It reads the most recently published view, so it
may omit accepted-but-pending rows. Omitting `refresh`, or choosing
`CountRefresh(every=1)`, preserves the existing eager behavior. v0.0 supports
only this synchronous count trigger; timers, background scheduling,
query-triggered refresh, and a crash-durable pending log remain future work.

LOTUS prompt batching is a separate, opt-in physical setting. `CountRefresh`
controls how many source rows enter one maintenance step; `PromptBatching`
controls how the independent semantic tasks that are ready inside one operator
invocation are placed into prompts:

```python
from agent_memory.adapters.lotus import LotusAdapter, PromptBatching
from agent_memory.adapters.lotus.context import LotusExecutionConfig

adapter = LotusAdapter(
    config=LotusExecutionConfig(
        prompt_batching=PromptBatching(),       # all ready tasks per prompt
        # prompt_batching=PromptBatching(max_tasks=8),
    )
)
memory = ClaudeMemory(
    adapter=adapter,
    refresh=am.CountRefresh(every=32),
)
```

The default `prompt_batching=None` preserves existing prompts. When enabled,
the adapter uses stable task IDs, deterministic context-bounded chunks, strict
output validation, and retries only failed chunks. Search-Filter still runs
before prompt construction. Prompt batching is also distinct from provider
request batching: the former puts several tasks in one prompt, while the latter
sends several unchanged prompts in one provider request. The physical setting
is recorded in the maintenance/checkpoint identity.

This setting is experimental and is not semantically transparent. Even when
every task payload is unchanged, placing several tasks in the same model
context can change extraction, matching, or aggregation decisions. Current
32-event Claude/Mem0/Zep evidence did not establish a safe system-wide batch
size, so `PromptBatching()` and `max_tasks` must remain explicit physical
experiment conditions rather than v0.0 defaults.

By contrast, `query(...)` is policy-owned retrieval behavior, but policy writers
do not override the method. A concrete memory policy declares a parameterized
class-body retrieval template. For Claude-style memory, retrieval selects from
a lightweight topic manifest, then uses a deterministic identity join to fetch
the full topic body. The framework-provided `Memory.query("...")` binds
`UserQuery` to the end-user text and executes the compiled retrieval template
against current materialized state.

Policy authors define memory policies with DataFrame-style view queries:

```python
import agent_memory as am


class ClaudeMemory(am.Memory):
    log = am.Log()

    topics = (
        log
        .sem_flat_map(
            output_cols={
                "name": "Candidate durable memory topic name.",
                "description": "One-line relevance description.",
                "type": "Claude memory type.",
                "body": "Candidate durable memory body.",
            },
            instruction=(
                "Extract zero or more durable memory topic candidates from "
                "{message}, filling {name}, {description}, {type}, and {body}."
            ),
        )
        .select(["name", "description", "type", "body"])
        .sem_groupby(
            input_cols=["name", "description", "type"],
            instruction="Rows whose {name}, {description}, and {type} refer to the same durable memory topic belong in one group.",
        )
        .sem_agg(
            input_cols=["name", "description", "type", "body"],
            output_cols={
                "name": "Canonical durable memory topic name.",
                "description": "One-line relevance description.",
                "type": "Claude memory type.",
                "body": "Merged durable memory content.",
            },
            instruction="Choose canonical memory fields and merge topic content.",
        )
        .select(["name", "description", "type", "body"])
    )

    catalog = (
        topics
        .sem_map(
            input_cols=["name", "description", "type", "body"],
            output_cols={
                "catalog_title": "Title shown in the memory catalog.",
                "hook": "One-line relevance hook.",
            },
            instruction="Produce one catalog row per topic.",
        )
        .select(["catalog_title", "name", "hook"])
    )

    retrieval_query = (
        topics.select(["name", "description", "type"])
        .sem_topk(am.UserQuery(), 5)
        .join(topics, on="name")
        .select(["name", "description:right", "type:right", "body"])
    )
```

In the built-in `ClaudeMemory`, `catalog` is the MEMORY.md index projection,
not the native-like retrieval selector source. Retrieval uses `topics` as the
topic manifest and joins back to `topics` to return body content. When selected
and fetched relations have overlapping non-key columns, deterministic
`join(on=...)` follows the `:left` / `:right` suffix convention; future
`rename`, `select_as`, or `lookup` sugar may clean up public output names.

Policy-author public objects:

- `am.Memory`
- `am.Log`
- `am.Message`
- `am.UserQuery`
- dataframe-style operators such as `select`, `filter`, `assign`, `concat`,
  `union`, `min`, and `subtract`
- aggregate specs such as `am.sem_agg(...)`, `am.array_agg(...)`,
  `am.collect_list(...)`, and `am.min(...)`
- scalar expressions such as relation-bound columns and `am.least(...)`
- semantic operators such as `sem_filter`, `sem_map`, `sem_flat_map`,
  `sem_groupby`, `sem_agg`, `sem_join`, and `sem_topk`

`sem_agg(...)` is a dataframe-style semantic operator. `Relation.sem_agg(...)`
means whole-relation aggregation; `GroupedRelation.sem_agg(...)`, produced by
`sem_groupby(...)`, means per-group aggregation. v0.0 uses the chain form
`sem_groupby(...).sem_agg(...)` for one aggregate and grouped `.agg(...)` with
explicit top-level aggregate specs for mixed aggregate output.

The policy-author query shape is DataFrame-first. v0.0 does not require users to
define Pydantic schemas or typed memory node classes. `am.Log()` uses a default
DataFrame-like log shape; explicit column declarations can be added later while
staying in DataFrame form.

### Logical Query Model

The logical query model is internal. It records the view definition queries
written through the authoring API.

Core objects:

- `Log`: base source relation, not a memory view.
- `Relation`: dataframe-like authoring handle returned by operators, not a
  top-level public object.
- `GroupedRelation`: intermediate chain handle returned by `sem_groupby(...)`;
  it becomes a normal `Relation` after `.sem_agg(...)`.
- `QueryExpr`: internal immutable query tree node for full view queries `Q`,
  differentiated maintenance queries `Q'`, and retrieval query templates.
- `MemoryView`: named derived memory view `V = Q(D)` collected from a `Memory` class.
- `MemorySpec`: collected declaration for one memory class.

`QueryExpr` should represent operators such as:

- source relations: `log`
- named memory view references
- ordinary operators: `select`, `filter`, `assign`, `concat`, `union`,
  `subtract`, `drop_duplicates`, `group_by`, `agg`, `array_agg`, `min`,
  `flatten`, `explode`, and `unnest`
- semantic operators: `sem_filter`, `sem_map`, `sem_flat_map`,
  `sem_groupby`, `sem_agg`, `sem_join`, `sem_topk`

`Relation` is the dataframe-like handle used while authoring a policy. It
exposes methods such as `sem_map`, `sem_groupby`, and `select`.
`QueryExpr` is the immutable query tree node inside a `Relation`; it records the
operator name, inputs, parameters, and column metadata. Policy authors use
relation methods, but they do not instantiate or inspect `QueryExpr`.
`Relation.expr` is currently readable as an internal observation detail for
tests and debugging, but policy authors should not treat it as stable public API.

Class body collection follows these rules:

- `am.Log()` defines the source relation. It is the base table, not a
  `MemoryView`.
- A class attribute whose value is a `Relation` and whose name starts with `_`
  is treated as a private intermediate relation. It can be referenced by later
  view definitions, but is not collected as a public memory view.
- A class attribute whose value is a derived `Relation` and whose name does not
  start with `_` is collected as a `MemoryView`.
- A class attribute named `retrieval_query` is collected as the default
  parameterized retrieval query template, not as a `MemoryView`.
- Non-`Relation` class attributes are ignored by the memory view collector.

For example, `log` is the source relation, and derived public memory relations
such as `topics` and `catalog` are collected as `MemoryView`s. A policy may also
declare private intermediate relations by prefixing a relation name with `_`.

`MemoryView` is the preferred name for named memory views. Avoid `ViewDef` in
v0.0 because the project vocabulary is memory-centered. Avoid `ViewGraph` in
v0.0; dependency information can be derived from `MemorySpec` and relation
expressions when needed.

### Differential Policy Compilation

`PolicyDifferentiator` is the policy-level internal `Q -> Q'` component.
Policy authors and end users normally call `Memory.differentiate_policy()`
instead. It uses `QueryDifferentiator` for single-view rewrite, then assembles
the full in-memory `DifferentiatedPolicy` artifact.

Responsibilities:

- accept a `MemorySpec` containing full view definition queries `Q`
- apply hardcoded differential rules from the golden theory document
- produce differentiated maintenance queries `Q'` for public views
- collect parameterized retrieval query templates
- compute exact public-view dependencies and a topological execution order
- keep rewritten instructions explicit and inspectable

v0.0 should implement rule-based rewrites directly in Python. It should not
introduce Calcite or a general rule engine yet.

The planner name should follow the theory vocabulary:

```python
class QueryDifferentiator:
    def differentiate(self, view: MemoryView) -> QueryExpr:
        ...
```

`differentiate(...)` derives a query template. It does not receive concrete
changed rows. Runtime binds the logical source input to the current
`changed_rows` batch when executing `Q'`.

v0.0 compilation unit:

- `QueryDifferentiator(...).differentiate(view)` produces `Q'` for one
  stateful operator pattern.
- `PolicyDifferentiator(...).differentiate(spec)` produces an in-memory
  `DifferentiatedPolicy` containing the shared executable nodes directly.
- Structurally equal subtrees are one node. Public views map to sink nodes, and
  runtime executes the finite DAG in stable topological order.
- v0.0 does not implement JSON/YAML artifact IO, full optimizer passes, or
  logical-equivalence dependency matching.

### Memory Runtime

`MemoryRuntime` orchestrates v0.0 execution.

Responsibilities:

- append new log rows
- normalize end-user append input such as string messages into the configured
  log columns
- optionally retain normalized rows until a configured count boundary or an
  explicit `flush()`
- propagate relation changes through the shared policy nodes
- execute each changed policy node at most once per published delta
- call an `ExecutionAdapter`
- stage and atomically commit public and private node state
- bind `UserQuery` placeholders in compiled retrieval templates
- support write-side maintenance for end-user methods such as `add(...)`

v0.0 runs one eager, sequential dataflow step per appended log row by default.
`CountRefresh(every=N)` may instead coalesce source rows into one synchronous,
atomic delta step. This is not a general lazy scheduler: time triggers,
background refresh, query-triggered refresh, freshness policies, concurrent
maintenance, and watermark-based scheduling remain future runtime work.

`MemoryRuntime` owns materialized memory state. `MemorySpec` remains the logical
policy declaration and should not carry runtime dataframe contents. The v0.0
interface layer keeps a private in-memory dataframe state for the HelloWorld
smoke. The intended state keys are `"log"` for the source log and
`MemoryView.name` values for public materialized views. Shared intermediate node
state is stored separately and never appears in public view schemas.

Retrieval remains policy-owned in v0.0. `MemoryRuntime` does not choose a target
view; it executes the compiled retrieval template declared as `retrieval_query`
after binding `UserQuery` to the end-user text.

Internal debugging hooks may exist during development, but `view(...)`,
`explain(...)`, and `explain_maintenance(...)` are not v0.0 public API.

### Execution Adapter

`ExecutionAdapter` is the internal boundary between agent-memory logical plans
and a semantic operator execution engine.

v0.0 should implement only:

- `LotusAdapter`

`LotusAdapter` lowers supported logical expressions to LOTUS-style dataframe
operators and executes them. v0.0 uses Lotus as the default semantic execution
mechanism internally. DeepSeek is only model/provider configuration inside this
adapter; it is not an agent-memory architecture layer.
The current adapter subset supports `log`, `materialized_view`, `select`,
`concat`, `union`, `subtract`, `drop_duplicates`, `sem_filter`, `sem_map`,
`sem_flat_map`, `sem_join`, `sem_groupby`, `sem_agg`, and `sem_topk`.
`filter(predicate=...)`, `assign(...)`, and predicate `join(...)` use a minimal
serializable relation-bound expression subset via `relation.col(...)`; arbitrary
Python callables, SQL strings, and tuple predicates are not part of the v0.0
contract.

LOTUS requires semantic top-k expressions to reference dataframe columns with
`{column}` placeholders; when runtime binds `am.UserQuery()` to plain end-user
text, the adapter lowers it to a column-aware LOTUS expression using the input
dataframe columns. For structured `sem_map` and `sem_flat_map`, the adapter
preserves the policy instruction and adds a backend JSON output constraint.
Decoded fields preserve JSON scalar types (`str`, number, boolean, or null);
nested values are rejected and may use the configured bounded retry.
For multi-output `sem_agg`, the adapter uses an agent-memory compatibility
helper that follows LOTUS main-style hierarchical aggregation and applies JSON
object `response_format` only on the final LM pass.

API keys should come from environment variables or the model provider's standard
configuration path. v0.0 may use Lotus plus DeepSeek for smoke demos, but
ordinary public examples should not require users to pass a `LotusAdapter`.

v0.0 adapter input contract:

- `query` is a logical `QueryExpr` produced by the policy compiler or planner.
- During dataflow maintenance, materialized inputs are keyed by stable node ID;
  a stateful `Q'` also receives the node's current state and its parent's inserted
  rows under compiler-owned names.
- During retrieval, inputs remain keyed by `"log"` and public
  `MemoryView.name` values.
- The runtime is responsible for populating inputs required by the expression;
  adapters may raise if a referenced input is missing.

## 3. V0.0 Execution Path

The intended flow is:

1. A policy author defines a subclass of `am.Memory`.
2. The authoring API builds `Relation` objects during class definition.
3. The memory class collector builds a `MemorySpec`, including public views and
   retrieval query templates.
4. The collector identifies derived memory views such as `topics` and `catalog`;
   private intermediate relations remain internal query expressions.
5. `PolicyDifferentiator` builds an in-memory `DifferentiatedPolicy` containing
   shared executable nodes.
6. `MemoryRuntime` loads that policy and receives new log rows.
7. `PolicyExecutor` propagates changes in node-topological order and invokes
   `LotusAdapter` for the required operator or `Q'`.
8. `MemoryRuntime` commits all next state only after the full step succeeds.
9. `Memory.query(...)` binds `UserQuery` and executes the compiled retrieval
   template.

Minimal usage:

```python
memory = am.ClaudeMemory()
memory.add(am.Message(content="Please remember that I prefer concise design docs."))
results = memory.query("design docs")
```

This is the intended surface. In the current v0.0 interface layer, runtime can
execute finite, non-recursive multi-view dataflows over the supported LOTUS
adapter operators. Storage, advanced scheduling, durable policy artifacts,
optimizer passes, source delete/upsert semantics, recursive/fixpoint queries,
standalone view-time `sem_join`, and view-time `sem_topk` remain out of scope.

Deterministic nodes currently recompute exact next state from their parents and
derive a multiset change. Stateful semantic aggregates use their declared
differential rules and may use compressed aggregate state; the runtime does not
silently turn unsupported semantic deletion into full recompute.

## 4. V0.0 Boundaries

Do not implement these in v0.0:

- user-defined schema classes
- DSPy prompt/program optimization
- lazy/eager/batched scheduler hierarchy
- multiple storage backends
- Calcite integration
- Palimpzest adapter
- graph/vector/markdown stores
- long-term persistence beyond in-memory dataframe state

These are future extension points, not empty interfaces that v0.0 must create.

The code should leave room for those extensions by keeping boundaries clean:

- planner logic should not import LOTUS directly
- adapter logic should not know about Python memory class collection
- runtime logic should call adapters through `ExecutionAdapter`
- model/provider config should stay inside adapter configuration
- memory state should be isolated enough to replace with storage backends later

## 5. Naming Summary

Preferred public / policy-author names:

- `Memory`
- `Log`
- dataframe-style ordinary operators
- dataframe-style semantic operators

Preferred internal engineering names:

- `Relation`
- `GroupedRelation`
- `QueryExpr`
- `MemoryView`
- `MemorySpec`
- `MemoryRuntime`
- `QueryDifferentiator`
- `PolicyDifferentiator`
- `ExecutionAdapter`
- `LotusAdapter`

Avoid in v0.0:

- `ViewDef`
- `ViewGraph`
- `SemanticMemoryView`
- `SemanticViewRuntime`
- `DspyOptimizer`
- `CalcitePlanner`
- `StorageBackend`
- `Scheduler`

Use `semantic` mainly for operators and execution semantics, not for every class
name.
