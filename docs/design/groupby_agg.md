# Grouped Aggregation

Grouping decides which rows belong together. Aggregation decides what one
group produces. Keep those two contracts separate when declaring a memory
view. General relation and window operators are in the
[Operator API](operator-api.md).

## Choose a grouping contract

| Grouping | How membership is decided | Aggregate output |
| --- | --- | --- |
| `group_by(keys)` | Exact key values | Exact keys plus aggregate columns |
| `sem_groupby(input_cols=..., instruction=...)` | Semantic matching | Canonical fields generated by the semantic aggregate |
| `sem_groupby(..., partition_by=keys)` | Exact partitions first, semantic matching within each partition | Partition keys and declared aggregate fields |
| `sem_groupby(..., labels=...)` | Assignment to a declared label | Declared aggregate fields; explicitly request the label if needed |

A semantic key is a matching input, not an automatically preserved original
value. Include every semantic key in the semantic aggregate's
`output_cols` so that a canonical group can be matched on later updates.

```python
import agent_memory as am

rows = am.Log({"name": "Entity mention.", "body": "Information about it."})
entities = rows.sem_groupby(
    input_cols=["name"],
    instruction="Group mentions of the same real-world entity.",
    membership="exclusive",
).sem_agg(
    input_cols=["name", "body"],
    output_cols={"name": "Canonical name.", "summary": "Consolidated information."},
    instruction="Choose a canonical name and retain the information in the group.",
)
```

`membership="exclusive"` declares at most one target group per incoming
group in join-map maintenance. `membership=None` retains the unrestricted
matching contract; static grouping still assigns one group ID per row.
`membership="overlapping"` is not implemented.

`partition_by` is appropriate for exact boundaries such as tenant or entity
endpoint IDs. It does not ask the model to infer those boundaries.
Physical pairwise/listwise resolution and embedding screening are separate
execution choices; neither defines group membership.

## Deterministic grouping with semantic content

Exact keys remain in the result:

```python
import agent_memory as am

rows = am.Log({"user_id": "User.", "day": "Calendar day.", "message": "Text."})
daily = rows.group_by(["user_id", "day"]).sem_agg(
    input_cols=["message"],
    output_cols={"summary": "Summary for this user and day."},
    instruction="Summarize the messages without inventing information.",
)
```

The schema is `user_id, day, summary`. In this direct `.sem_agg(...)`
form, an aggregate output with the same name as an exact key does not replace
that key. Prefer distinct output names so the intended schema is explicit.

## Combine semantic and deterministic outputs

`grouped.agg(*specs)` accepts aggregate descriptors exported by
`agent_memory`. One group can produce synthesized content and deterministic
provenance:

```python
import agent_memory as am

rows = am.Log({
    "name": "Entity mention.",
    "body": "Information.",
    "source_id": "Source identifier.",
})
entities = rows.sem_groupby(
    input_cols=["name"],
    instruction="Group mentions of the same real-world entity.",
    membership="exclusive",
).agg(
    am.sem_agg(
        input_cols=["name", "body"],
        output_cols={"name": "Canonical name.", "summary": "Combined information."},
        instruction="Consolidate the group's information.",
    ),
    am.array_agg(columns=["source_id"], output_col="sources"),
)
```

All specs use the same group membership. Semantic fields come from the model;
`sources` comes from the actual grouped rows. Declared output names must be
unambiguous. Prefer names that do not collide with exact grouping keys.

| Descriptor | Contract |
| --- | --- |
| `am.sem_agg(input_cols=None, output_cols=..., instruction=...)` | Synthesize declared columns; `output_cols` is required for the descriptor |
| `am.array_agg(columns=..., output_col=...)` | JSON array of records; preserves contributions |
| `am.collect_list(column=..., output_col=...)` | JSON list of values, including nested values |
| `am.min(column=..., output_col=...)` | Minimum non-null value |
| `am.min(columns=..., output_col=...)` | Lexicographically minimum complete tuple |

For semantic grouping, mixed `.agg(...)` requires at least one
`am.sem_agg`, and all semantic key names must be among its outputs.
A semantic group cannot be closed using only `.array_agg` or `.min`.
For exact grouping, those direct methods are supported.

Scalar `min` ignores nulls; composite `min` skips rows with any null
component. An empty global input or an all-null group produces null, while an
empty grouped input produces no groups. Supply exactly one of `column` or
`columns`. This is different from `least`, which compares values in a row.

## Numeric aggregation

Global relations and exact groups support `count`, `sum`, and `avg`:

```python
import agent_memory as am

rows = am.Log({"category": "Category.", "amount": "Numeric amount."})
totals = rows.group_by("category").agg(
    am.count(output_col="n"),
    am.sum(column="amount", output_col="total"),
    am.avg(column="amount", output_col="mean"),
)
```

`count` counts rows, including rows with null values. `sum` and `avg`
use non-null numeric values; an all-null input produces null for those
aggregates. Global count over empty input is zero. Grouped empty input has no
groups. Numeric fields must contain numeric values; schema descriptions are
not implicit casts.

Numeric aggregate specs can be combined with each other, but not with semantic,
array, list, or minimum specs in one aggregate call. They are not supported on
semantic groups. Global `Relation.agg` accepts only the numeric spec family.

## Maintenance

The default grouped-aggregate rule is `rule-join-map`. Conceptually it matches
incoming group information to existing groups and then constructs updated
group content. A match updates a group; unmatched new information can create a
group; untouched old groups remain. Exclusive membership bounds the match to
one old target. Exact partitions remain exact throughout maintenance.

The public view still declares grouping and aggregation. The compiler creates
the maintenance expressions, including semantic joins and maps; applications
do not need to implement an update loop for each aggregate.
Source changes, output identities, and downstream dependencies are runtime
responsibilities.

Deterministic aggregates use their own state: arrays preserve contributions,
minima retain the information needed for their updates, and numeric aggregation
maintains counts and sums as appropriate. These are not model-generated
estimates.

Semantic consolidation relies on the retained group content and matching
instruction. Different model decisions or lossy summaries can produce
different results from fresh evaluation over all source rows. Evaluate a
selected rule and model together rather than treating all semantic aggregates
as associative numeric reductions.

For alternative rule selectors accepted by this checkout, use the
[configuration reference](../configuration.md). A selected rule must support
the policy shape; compilation does not silently substitute another rule.

## Output checklist

- Semantic keys appear in semantic aggregate outputs.
- Exact partitions and deterministic group keys have explicit roles.
- Provenance uses deterministic aggregation rather than generated identifiers.
- Numeric, record-array, value-list, and scalar outputs are not interchanged.
- Retrieval consumes the final public view, not temporary group IDs.
- The chosen maintenance rule compiles before a model-backed run starts.
